# 역사 지도 (History Map) — 설계 문서

> 상태: 초안 v0.1 · 2026-09-25

## 1. 개요

연도를 고르면 그 시기의 세계 지도가 나라 단위 블럭으로 나타나는 웹 서비스다. 나라를 누르면 그 시기의 사건 목록이 나오고, 사건 위에 마우스를 올리면 그 사건에 영향을 준 나라와 영향을 받은 나라를 화살표로 보여준다.

- **최종 목표**: 전 세계 역사 지도
- **1차 목표**: 지도 틀은 전 세계로 만들고, 데이터는 한국사부터 채운다
- **확장 계획**: 나라 단위에서 지역 단위(도, 주 등)로 내려간다

### 3.1 도법을 정한 과정 (D13)

- **처음(P0~P2)**: Equal Earth에 중앙 경선을 동경 120°로 고정했다. 동아시아는 괜찮았지만 유럽·아메리카가 가장자리에서 비스듬히 기울어졌다.
- **지구본**: 모양은 정확하지만 한 번에 지구 절반만 보여서, 나라 사이의 관계를 한눈에 보기 어려워 제외했다.
- **메르카토르(좌우 이어짐)**: 모양이 정확하고 가볍지만, 위도가 높을수록 면적이 크게 부풀려진다(북위 50°에서 약 2.4배, 65°에서 약 5.6배). 북방 유목 제국과 중원 왕조처럼 위도가 다른 세력의 크기를 비교할 수 없게 되어 역사 지도에 맞지 않아 제외했다.
- **채택**: 면적 보존 도법을 유지하되 중앙 경선을 화면 가운데로 계속 옮긴다. 크기는 정확하고, 보는 곳의 모양도 정확하다. 대신 움직일 때마다 지도 전체를 다시 계산해야 해서 아래 성능 대책이 필요하다.
- **위아래 회전(사축)**: 위아래도 도법 회전으로 이으면 극지방까지 왜곡이 줄지만, 고위도에서 북쪽이 기울고 극을 넘으면 뒤집혀 가시성과 조작감이 나빴다 (테스트 후 운영자 판단으로 제외).
- **확대하면 지역 도법으로 (2026-09-26 적용)**: Equal Earth는 위도가 높을수록 모양이 가로로 눌려 유럽·북방 지역이 왜곡된다. 그래서 확대할수록 **람베르트 정적 방위 도법**(보는 곳 중심, 유럽연합 공식 지도 표준 ETRS89-LAEA와 같은 도법)으로 두 도법의 좌표를 섞어 부드럽게 바꾼다 (Jenny 2012, "Adaptive Composite Map Projections"의 방식을 단순화).
  - 두 도법 모두 면적을 보존하므로 나라 크기 비교 원칙이 유지되고, 확대 상태에서도 북쪽은 항상 위다.
  - 바뀌는 시점: 지도 축척(s0·k)이 화면 긴 변의 **0.45배에서 섞기 시작해 0.65배에서 완료** (PC 2096×1102에서 대략 배율 2.5~3.5). 배율 고정값으로 정하면 좁은 모바일 화면에서 지구 반대편 가장자리가 보여서 화면 크기에 대한 비율로 정한다.
  - 자르기: 지역 도법이 절반 넘게 섞이면 경도 180° 선 대신 **중심에서 170° 떨어진 원**으로 자른다 (방위 도법에서는 경도 180° 선이 한 줄로 겹쳐 지도가 사라지기 때문).
  - 섞은 도법은 역변환 공식이 없어 **뉴턴법**으로 화면 좌표 → 경위도를 구한다 (나라 클릭, 끌기, 화면 밖 판정). 되돌리기 오차 0px로 검증.
  - 휠·핀치 확대는 기준점(포인터) 아래의 땅이 제자리에 남도록 시점을 보정한다 (`zoomAround`). 보정 전에는 1.25배 확대마다 11~60px 밀렸고, 보정 후 1px 이내.
  - 시점 저장 방식(중심 경도, 배율, Equal Earth 기준 적도의 화면 y)은 그대로 두고 투영을 만들 때만 섞는다. 그래서 축소 시 지도 끝 붙이기(§6.6)와 버튼 이동은 바뀌지 않았다.

### 3.2 성능 측정과 대책

GDP 상위 50개국 역사를 모두 넣은 상황을 가정한 가짜 데이터(나라 300개, 공유 국경 포함)로, 옆으로 1.5°씩 120프레임을 돌리며 측정했다 (Ryzen 7 5700G, 60Hz, 2096×1102).

| 방식 | 그리는 점 | 한 프레임 계산 | 결과 |
|------|-----------|----------------|------|
| SVG · 1:50m 원본 | 약 16.9만 | 119ms | 7.9fps |
| Canvas · 1:50m 원본 | 약 16.9만 | 117ms | 8.5fps (병목은 그리기가 아니라 도법 계산) |
| Canvas · 1:50m 원본 · 곡선 보정 끔 | 약 16.9만 | 100ms | 9.9fps |
| Canvas · 간략(1:110m + 단순화) | 약 2.1만 | 12.6ms | 60fps |
| Canvas · 간략 · 곡선 보정 끔 | 약 2.1만 | 7.7ms | 60fps |
| Canvas · 초간략 · 곡선 보정 끔 | 약 1.3만 | 5.8ms | 60fps (모바일 예상 35~60fps) |
| SVG · 초간략 · 곡선 보정 끔 | 약 1.3만 | 8.7ms | 60fps |

**대책**
1. **곡선 보정(적응형 재표본화) 끔**: 데이터 점이 이미 촘촘해서 화질 차이가 없고 계산이 약 40% 준다.
2. **정밀도 단계(LOD) 3단계**를 빌드에서 미리 만든다 (`low`: 1:110m + 강한 단순화, `mid`: 1:50m + 약한 단순화, `high`: 1:50m 원본).
   - 움직이는 중: 배율 4 미만 `low`, 12 미만 `mid`, 그 이상 `high`
   - 멈춘 뒤(150ms): 배율 2 미만 `mid`, 그 이상 `high`
3. **화면 밖 도형은 계산하지 않는다**: 영토와 육지 조각마다 경위도 범위를 두고, 화면에 보이는 범위와 겹치는 것만 그린다.
4. **Canvas + SVG 혼합**: 같은 조건에서 Canvas가 SVG보다 약 1.5배 빠르다. 모바일 여유를 위해 무거운 층만 Canvas로 둔다.
5. **확대했을 때는 격자 조각으로 그린다 (2026-09-26 적용)**: 3번만으로는 유라시아처럼 큰 도형이 조금만 보여도 통째로 계산된다. 그래서 `mid`·`high` 단계의 육지와 영토를 10°×10° 조각(칠하기용)과 64점 선 조각(테두리용)으로도 만들어 둔다.
   - 빌드: `land-tiled-<lod>.topo.json`, `geo-tiled/<lod>/<entityId>.topo.json`. 조각과 선 조각을 한 토폴로지로 묶어 용량 증가를 줄인다(정밀 단계 육지 547KB → 965KB). 자르기는 축에 나란한 사각형 전용 알고리즘(Sutherland–Hodgman)으로 해서 빌드 시간이 약 10초 → 18초로 늘어나는 데 그친다 (일반 폴리곤 연산으로는 240초).
   - 앱: 화면에 보이는 경위도 넓이(경도 폭 × 위도 폭)가 **3000도² 이하**일 때만 조각을 불러와 보이는 조각만 그린다. 조각은 자른 면과 따로 그리는 테두리 때문에 점이 약 2배라, 넓게 볼 때는 오히려 느리다(테스트에서 배율 3에서 10 → 21ms). 경도 폭만 기준으로 하면 세로로 긴 화면에서 너무 일찍 켜져서 넓이로 판단한다.
   - 같은 나라의 조각은 한 경로로 칠해 조각 사이 이음매가 보이지 않게 하고, 테두리는 선 조각으로 그려 격자 칸 경계가 드러나지 않게 한다. 클릭 판정과 hover 테두리는 원래 도형을 쓴다.
   - 측정 (실제 1280년 데이터, 움직이는 중, 370×417 화면): 배율 2·6은 차이 없음(조각 미사용), 배율 9에서 21.0 → 5.1ms, 12에서 25.3 → 5.1ms, 20에서 26.0 → 4.3ms. 가짜 300개국 데이터(2096×1102)에서는 배율 6에서 68.3 → 20.0ms.
6. **확대하면 지역 도법 (2026-09-26 적용, §3.1)의 성능 비용**: 테스트(가짜 300개국, 격자 조각 사용)에서 지역 도법은 Equal Earth보다 약 33% 무거웠다 (배율 6에서 20.0 → 26.7ms). 섞는 구간은 두 도법을 모두 계산해 약 60% 무겁지만 구간을 좁혀 지나는 시간을 줄였다.

## 4. 데이터 모델

### 4.1 핵심 개념

```
Entity (나라·지역)  ──1:N──  Territory (기간별 영토 폴리곤)
   │
   ├──N:M── Relation (기간별 관계: part_of, occupied_by, vassal_of, successor_of)
   │
Event (사건) ── subjects / influencedBy / influences ──> Entity
```

**Entity**라는 하나의 개념을 `level`로 나눈다. 나라와 지역을 같은 구조로 다루기 때문에 지역 단위로 확장할 때 모델을 바꿀 필요가 없다.

### 4.2 스키마 (TypeScript 표기)

```ts
type Year = number; // 천문 연도: 기원전 1년 = 0, 기원전 57년 = -56. 표시할 때만 변환한다.

interface Entity {
  id: string;                    // 'silla', 'goguryeo', 'tang', 'gyeonggi-do'
  level: 'polity' | 'region';    // 앞으로 'subregion' 등 추가 가능
  names: { ko: string; en?: string; hanja?: string; [lang: string]: string | undefined };
  from: Year;                    // 존속 첫해 (포함)
  to: Year | null;               // 존속 마지막 해 (포함, 예: 고구려 668). null이면 현재까지
  color?: string;                // 없으면 빌드에서 이웃과 겹치지 않게 자동 배정
  summary?: string;
  basis: {                       // 수록 근거 (D9). level이 'polity'면 필수
    type: 'primary_source' | 'national_institution';  // 사료로 확인 / 그 나라 역사기관이 인정
    refs: string[];              // 예: '삼국유사 권1 기이편', '국사편찬위원회 우리역사넷'
    foundingNote?: string;       // 건국 연대가 전승에 기반한 경우 설명 (예: 고조선 BC 2333)
  };
}

interface Territory {            // GeoJSON Feature의 properties
  entityId: string;
  from: Year;                    // 구간 [from, to)
  to: Year | null;
  certainty: 'confirmed' | 'estimated' | 'disputed';  // 경계 표시 스타일(실선/점선)에 사용
  source: string;                // 출처 (도서, 지도집 등)
}

interface Relation {
  type: 'part_of' | 'occupied_by' | 'vassal_of' | 'successor_of';
  subject: string;               // entityId
  object: string;                // entityId
  from: Year;
  to: Year | null;
}

interface Event {
  id: string;
  year: Year;
  endYear?: Year;                // 전쟁처럼 기간이 있는 사건
  precision: 'year' | 'decade' | 'century';
  title: { ko: string; en?: string };
  summary: { ko: string; en?: string };
  subjects: string[];            // 이 사건이 목록에 나오는 나라·지역
  links: EventLink[];            // 영향 관계 (방향이 있는 화살표)
  location?: { entityId?: string; point?: [lon: number, lat: number] };  // (예정)
  tags?: string[];               // 'war', 'diplomacy', 'culture', ...
  sources: string[];             // 필수
}

interface EventLink {
  from: string;                  // 영향을 준 나라
  to: string;                    // 영향을 받은 나라
  note?: string;                 // "김춘추의 외교" 같은 화살표 라벨
}
```

**`subjects`가 배열인 이유**: 백강 전투처럼 여러 나라에 걸친 사건을 한 번만 작성하고 여러 나라의 목록에 나오게 하기 위해서다.

**영향 관계를 `from → to` 쌍으로 적는 이유**: 처음 설계는 `influencedBy`/`influences` 두 목록이었는데, 이 방식은 "누구 입장에서" 들어오고 나가는지가 사건마다 하나로 고정된다. 여러 나라가 얽힌 사건(예: 백강 전투의 왜·당·신라)에서는 선택한 나라마다 방향이 달라야 하므로, 방향이 있는 쌍으로 적고 화면에서 선택한 나라 기준으로 나눈다.
- 선택한 나라가 `to`인 link → 들어오는 화살표 (파랑 실선)
- 선택한 나라가 `from`인 link → 나가는 화살표 (주황 점선)
- 선택한 나라와 무관한 link → 화살표 없이 목록에만 회색으로 표시

### 4.3 관계와 렌더링 규칙

| Relation | 의미 | 렌더링 |
|----------|------|--------|
| `part_of` | 지역이 나라에 속함 (기간 한정) | 지역 레이어의 계층 구성, 사건 집계 |
| `occupied_by` | 점령·강점 (예: 웅진도독부·안동도호부 → 당, 일제강점기 한국 → 일본) | 자체 색 위에 지배국 색 빗금 (구현됨, 화면 기준 7px 간격 대각선). 패널에 "○○의 점령지" 표시 |
| `vassal_of` | 종속·간섭 관계 (원 간섭기 등) | 테두리를 지배국 색으로 굵게 표시 (빗금보다 약한 표현, 구현됨). 패널에 "○○의 간섭·종속" 표시 |
| `successor_of` | 계승 (고구려 → 발해) | 선택한 나라가 사라진 연도로 이동하면 "후계 국가로 이동" 링크 제공 |

### 4.4 시간 처리

- 모든 데이터는 1년 단위로, 구간 `[from, to)`로 저장한다.
- 연도 Y의 지도는 `from ≤ Y < to`인 Territory들의 모음이다. 국경은 다음 변화가 있을 때까지 유지된다 (스냅샷 + 유효기간).
- 슬라이더는 10년 단위로 움직이지만 내부 상태는 1년 단위다. "다음 변화" 버튼은 빌드 시 계산한 변경 연도 목록으로 이동한다.
- 10년 구간은 `floor(Y / 10) * 10`부터 9년 뒤까지다 (예: 660–669).

## 5. 데이터 제작과 빌드 파이프라인

### 5.1 저장소의 원본 데이터 구조

```
data/
  entities/        # 나라·지역 정의 (YAML, 권역별 파일)
    korea.yaml
    china.yaml
    japan.yaml
    steppe.yaml
  relations.yaml
  events/          # 사건 (YAML, 시대별 파일)
    gojoseon.yaml
    three-kingdoms.yaml
    ...
  geo/             # 영토 폴리곤 (Entity 하나당 GeoJSON 파일 하나, feature마다 기간 속성)
    silla.geojson
    goguryeo.geojson
    ...
  base/            # Natural Earth 해안선·육지 (퍼블릭 도메인)
```

GeoJSON은 QGIS에서 바로 열고 편집할 수 있고, 텍스트 파일이라 git에서 변경 내용을 비교할 수 있다.

### 5.2 국경 작도 방식 (D2 작업량 줄이기)

1. **바다 쪽은 대충 그린다**: 나라 폴리곤을 해안선 바깥 바다까지 넉넉하게 그리면, 빌드 단계에서 Natural Earth 육지와 교차시켜 해안선을 자동으로 정확하게 맞춘다. 사람이 신경 쓸 부분은 **육상 국경선**뿐이다.
2. **이웃 나라와는 스냅으로 공유한다**: QGIS의 위상 편집을 켜서 국경을 공유하게 한다.
3. **변화가 있을 때만 새 버전을 만든다**: 이전 버전을 복사해 바뀐 부분만 고친다.
4. **빌드 검증기가 실수를 잡는다** (§5.3).

### 5.3 빌드 단계 (`npm run build:data`)

```
원본 YAML/GeoJSON
  → ① 스키마 검증 (zod)
  → ② 참조 무결성 검사
        - 사건의 subjects와 links가 가리키는 Entity가 사건 연도에 존재하는가
        - 같은 Entity의 Territory 기간이 서로 겹치지 않는가
        - 존속 기간 안에 영토가 비어 있는 구간이 없는가 (경고)
  → ③ 지오 처리
        - 해안선 클리핑
        - 서로 다른 나라 폴리곤의 겹침 검사 (면적 임계값을 넘으면 오류)
        - 지역이 모든 영토를 덮으면 나라 폴리곤은 지역 폴리곤을 합쳐서 만듦 (§7)
        - 정밀도 단계(low/mid/high)별로 육지와 모든 영토 버전을 **하나의 토폴로지**로 묶어 단순화 (§3.2)
        - 화살표 기준점 계산: polylabel (오목한 모양에서도 영토 안쪽에 찍힘)
        - 색상 자동 배정 (이웃 나라끼리 다른 색이 되도록 그래프 채색)   (예정: 지금은 color 미지정 시 기본 팔레트 순환)
  → ④ 출력 (public/data/)
        - timeline.json              : 타임라인 범위, 지도가 바뀌는 연도 목록
        - territories.json           : 영토 버전 목록 (나라, 기간, 확실성, 기준점, 경위도 범위)
        - geo/<lod>/<entityId>.topo.json : 나라별 영토 도형 (버전마다 한 번씩만 저장)
        - land-<lod>.topo.json       : Natural Earth 육지
        - entities.json, relations.json
        - events.json                : 전체 사건 (커지면 시대별 파일로 나눔)
```

- **영토는 나라별로 한 번씩만 저장한다.** 처음에는 국경이 바뀔 때마다 세계 전체 지도를 파일 하나로 만들었는데, 50개국 규모에서는 바뀌지 않은 나라까지 수천 번 반복 저장되어 0.3~1.2GB(GitHub Pages 한도 1GB)가 될 것으로 추정됐다. 지금은 브라우저가 `territories.json`에서 그 해의 버전을 골라 나라별 파일을 모아 그린다. 한 번 받은 파일은 다른 연도에서도 다시 쓴다.
- **단계마다 하나의 토폴로지로 묶는 이유**: 이웃 나라가 공유하는 국경과 버전 사이에 바뀌지 않은 국경이 한 번만 저장되고, 단순화해도 공유 경계가 양쪽에서 똑같이 바뀌어 틈이나 겹침이 생기지 않는다. 나라별 파일은 이 토폴로지에서 필요한 선만 골라 나눈 것이라 좌표가 정확히 일치한다.
- 해안선 클리핑은 화면의 육지와 같은 Natural Earth를 쓴다(`low`는 1:110m, 나머지는 1:50m). 해안선이 정확히 겹쳐야 영토와 회색 육지 사이에 틈이 보이지 않기 때문이다.
- 빌드 스크립트는 TypeScript로 작성하고 Node 24의 타입 제거 기능으로 바로 실행한다. 앱과 같은 zod 스키마(`src/schema`)를 쓴다.

### 6.1 블럭 hover
- 마우스 아래의 나라는 화면 좌표를 경위도로 되돌린 뒤, 그려진 영토 중 경위도 범위가 맞는 것만 골라 포함 여부를 검사해 찾는다 (Canvas에는 요소별 이벤트가 없으므로).
- 찾은 영토의 **경계선을 Canvas 위의 SVG 레이어에 진하게** 그린다. 위 레이어에 있으므로 이웃 영토에 가려지지 않는다.
- 처음에는 영토를 1.05배 키우는 효과도 있었으나, 운영자 요청으로 없애고 경계선 강조만 남겼다 (2026-09-25).
- 툴팁으로 국호와 존속 기간을 보여준다 (마우스일 때만).
- `certainty`가 `estimated`·`disputed`인 영토는 점선 테두리로 그린다.

### 6.2 블럭 클릭 → 사건 패널
- 오른쪽 패널에 국호, 존속 기간, 현재 10년 구간의 사건을 보여준다 (D6).
- 사건이 없으면 "이 구간에 등록된 사건 없음"과 함께 가장 가까운 사건으로 가는 링크를 보여준다.
- "이 나라 전체 사건 보기"를 누르면 존속 기간 전체를 연도순으로 보여주고, 현재 구간은 강조한다.
- 연도를 바꿨을 때 선택한 나라가 사라지면 패널에 "이 시기에는 존재하지 않음"을 표시하고 `successor_of` 링크를 보여준다.

### 6.3 사건 hover → 화살표
- **들어오는 화살표** (`to`가 선택한 나라인 link): 영향을 준 나라의 기준점 → 선택한 나라의 기준점. 색 A (파랑 계열)
- **나가는 화살표** (`from`이 선택한 나라인 link): 선택한 나라 → 영향을 받은 나라. 색 B (주황 계열)
- 색만으로 구분하지 않고 **선 모양도 다르게** 한다 (실선과 점선). 색각이상 사용자를 위한 것이다.
- 같은 두 나라 사이에 양방향 화살표가 생기면 서로 반대쪽으로 휜 곡선(2차 베지어)으로 그려 겹치지 않게 한다.
- 화살표 중간에 `note` 라벨을 붙인다.
- 상대 나라가 화면 밖에 있으면 화면 가장자리까지 그리고 국호 라벨을 붙인다.
- 기준점은 **사건 연도 기준**으로 정한다. 현재 화면 연도가 아니라 그 사건이 일어난 해의 영토를 쓴다. 그 해에 영토가 없으면(예: 멸망한 해의 고구려) 시간상 가장 가까운 영토 버전을 쓴다.
- 화살표와 이름표는 Canvas 위의 SVG에 화면 좌표로 그린다. 확대해도 선 굵기와 화살촉, 글자 크기가 변하지 않는다.
- 화면 밖 상대 나라를 가장자리 라벨로 표시하는 기능은 아직 없음 (예정).

### 6.4 기타
- **URL 상태**: `?year=668&entity=silla&event=baekgang-663` 형태로 링크 공유
- **다국어**: 데이터에 `names`와 `title`의 언어별 필드를 두고, UI 문자열은 i18n 키로 관리. 처음에는 한국어만.

### 6.6 축소할 때 지도 끝을 화면 경계에 붙이기

축소해서 지도 밖 빈 곳이 보이려 하면 지도 끝을 화면 경계에 붙인다 (`view.ts`의 `constrain`).

| 상황 | 동작 |
|------|------|
| 위(또는 아래) 끝이 화면 안으로 들어오려 함 | 그 끝을 화면 위(아래) 경계에 붙인 채 축소 |
| 지도 높이가 화면보다 작아짐 | 세로 가운데에 고정 |
| 세계 폭이 화면보다 좁을 때 축소하다 왼쪽(오른쪽) 끝이 화면 경계에 닿음 | 그 끝을 경계에 붙인 채 축소 (빈 곳은 반대쪽에만) |
| 세계 폭이 화면보다 넓음 | 좌우는 도법 회전으로 끝없이 이어지므로 끝이 없음 |

- **끌기는 항상 도법 회전**이다. 회전은 지도(타원) 위치를 바꾸지 않으므로 빈 곳을 만들지 않는다. 세계 전체가 보일 만큼 축소해도 좌우로 끌면 지구가 제자리에서 돈다.
- 세계 폭이 화면보다 좁을 때 **확대·축소만** 지도를 가로로 옮긴다(포인터 기준 확대). 다시 확대해서 세계 폭이 화면보다 넓어지면, 남은 가로 어긋남은 도법 회전으로 넘겨 화면이 튀지 않게 한다.
- 이 계산을 픽셀 단위로 정확히 하려고 시점을 `{ 중앙 경선의 경도, 배율, 적도의 화면 y, 가로 어긋남 px }`로 저장한다.
- 최대로 축소하면(배율 1) 세계가 화면 가로나 세로 한쪽에 여백 없이 꼭 맞는다.
- **확대해서 지역 도법(§3.1)이 섞이면 위·아래 끝 제한을 푼다** (2026-09-26 수정). 끝 제한은 Equal Earth 기준인데, Equal Earth는 극지방을 세로로 누르므로 그대로 두면 확대할수록 극점이 화면 밖으로 밀려났다 (1400×800, 배율 10에서 북극이 화면 위로 약 680px 밖). 지금은 섞인 정도(t)에 비례해 화면 높이의 절반까지 더 끌 수 있어서, 완전히 바뀌면(t=1) 극점을 화면 가운데까지 옮길 수 있다. 끝 붙이기는 세계 도법으로 보는 축소 상태에서만 원래대로 동작한다.
- 극점을 넘어 반대편을 잡고 끌면 중심 경도가 180° 뒤집혀 지도가 갑자기 돌아가므로, 극점에서 멈춘다 (`recenter`).
- 극점이 화면 안에 있으면 화면 격자 점만으로는 보이는 경도 범위를 놓치므로, 그리기 대상 판정(`visibleBounds`)에서 모든 경도를 그린다.

## 7. 지역 단위 확장 설계

처음부터 아래 원칙을 지켜서 나중에 모델을 바꾸지 않게 한다.

1. **지역도 Entity다**: `level: 'region'`으로 두고, `part_of` 관계로 기간별 소속 나라를 지정한다. 역사적 행정구역은 시대마다 다르다 (신라 9주, 고려 5도 양계, 조선 8도, 현대 도). 그래서 "현대 경기도"를 과거로 늘려 쓰지 않고 **시대별 지역 Entity를 따로 만든다**.
2. **나라 폴리곤은 가능하면 지역 폴리곤에서 만든다**: 어떤 기간에 지역이 나라 영토를 모두 덮으면 빌드에서 합쳐서 나라 폴리곤을 만든다. 원본을 하나로 유지해서 둘이 어긋나는 일이 없게 한다. 지역 데이터가 없는 기간에는 직접 그린 나라 폴리곤을 쓴다.
3. **사건은 어느 단위에든 붙일 수 있다**: `subjects`에 지역 id를 넣으면 그 해의 `part_of`를 따라 상위 나라의 목록에도 자동으로 올라간다.
4. **화면 전환**: 선택한 나라를 확대하거나 더블클릭하면 그 나라의 지역 레이어를 불러와 드릴다운한다. 출력 파일도 `map/<level>/<from>_<to>.topo.json` 형태로 단위별로 나눈다.
5. **화살표도 단위를 따른다**: 지역 단위 보기에서는 지역 기준점을 쓴다.

## 11. 수록 기준과 제보 절차

### 11.1 수록 기준 (D9)
- 타임라인은 **BC 2333(천문 연도 -2332)** 부터 시작한다.
- 나라(Entity)는 다음 중 하나를 만족할 때만 추가한다.
  - `primary_source`: 사료로 존재가 확인됨
  - `national_institution`: 그 나라의 공식 역사기관(한국은 국사편찬위원회 등)이 인정함
- 고조선의 건국 연대처럼 전승에 근거한 연대는 `foundingNote`에 그 사실을 적고, 패널에 "건국 연대는 『삼국유사』의 기록에 따름"처럼 보여준다. 초기 영토는 `certainty: 'estimated'`로 점선 표시한다.
- 빌드 검증기는 `basis.refs`가 비어 있는 나라를 오류로 처리한다.

### 11.2 제보 절차 (D10)
- 외부 기여자는 저장소를 직접 수정하지 않는다. **GitHub Issue 양식**으로만 제보를 받는다.
- 이슈 양식의 필수 항목: 대상 연도와 나라, 제보 내용, **증거 사료(서명, 권·쪽 또는 기관 자료 링크)**
- 운영자가 사료를 확인한 뒤 **자기 문장으로 새로 작성해** 반영한다. 제보자의 글을 그대로 복사하지 않는다. 이렇게 하면 모든 데이터의 저작권이 운영자 한 명에게 남아서 나중에 라이선스를 바꿀 수 있다 (§12).
- 반영된 항목의 `sources`에 사료를 적고, 원하면 제보자를 `CREDITS.md`에 기록한다.

## 12. 라이선스 (D11)

| 대상 | 라이선스 | 파일 |
|------|----------|------|
| 소스 코드 (`src/`, `scripts/`) | MIT | `LICENSE` |
| 직접 만든 데이터 (`data/entities`, `data/events`, `data/geo`, `relations.yaml`) | CC BY-NC-SA 4.0 | `data/LICENSE` |
| Natural Earth 해안선 (`data/base`) | 퍼블릭 도메인 | 출처만 표기 |

**데이터에 CC BY-NC-SA 4.0을 고른 이유**
- **BY (출처 표시)**: 다른 곳에서 쓸 때 이 프로젝트를 출처로 밝혀야 한다.
- **NC (비영리)**: 다른 사람이 운영자의 작업물로 상업 서비스를 만들 수 없다. 운영자 본인은 저작권자이므로 이 제한을 받지 않는다.
- **SA (동일 조건)**: 수정해서 배포하면 같은 라이선스를 따라야 하므로 폐쇄된 파생본이 생기지 않는다.
- **나중에 풀 수 있다**: 모든 데이터를 운영자 혼자 작성하므로(§11.2) 나중에 CC BY-SA나 CC BY처럼 더 개방적인 라이선스로 바꿀 수 있다. 반대로 한 번 개방한 버전은 되돌릴 수 없으므로 제한이 있는 쪽에서 시작한다.
- 역사적 사실 자체는 저작권 보호 대상이 아니다. 보호되는 것은 운영자가 쓴 서술 문장과 직접 그린 국경 폴리곤이다.

코드에 MIT를 쓰는 이유는 지도 렌더링 코드는 보호할 가치보다 공개해서 얻는 이점이 크고, 데이터와 분리해 두면 코드만 가져가도 데이터는 따라가지 않기 때문이다.

## 13. 배포 (D12)

- **GitHub Pages + GitHub Actions**: `main`에 push하면 `build:data` → `vite build` → Pages에 배포한다. 빌드 결과물(`public/data/`)은 저장소에 커밋하지 않는다.
- **경로**: 프로젝트 페이지는 `https://<사용자명>.github.io/history-map/`이므로 Vite의 `base`를 `/history-map/`로 설정하고, 데이터 요청도 이 경로 기준으로 만든다.
- **라우팅**: Pages는 SPA 경로 재작성을 지원하지 않으므로 화면 상태는 쿼리 문자열(`?year=668&entity=silla`)만 쓴다 (§6.4와 일치).
- **저장소 공개 여부**: 무료 계정에서 Pages를 쓰려면 저장소가 공개여야 한다. 그래서 워크플로(`.github/workflows/deploy.yml`)는 저장소 공개 여부에 따라 동작이 달라진다.
  - 비공개일 때: push와 PR마다 빌드와 데이터 검증만 실행하고 배포 단계는 건너뛴다.
  - 공개일 때: `main`에 push하면 배포까지 한다.
  - 공개로 전환한 직후 **Settings → Pages → Source를 "GitHub Actions"로 한 번 설정**해야 한다. 이 설정은 무료 계정의 비공개 저장소에서는 열리지 않고 워크플로가 대신 켤 수도 없다.
  - 공개 후에도 데이터는 CC BY-NC-SA로 보호된다.
- 빌드 검증(§5.3)이 실패하면 배포하지 않는다.
